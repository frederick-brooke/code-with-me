# ADR-0003: Prisma 7 + Postgres as the durable data layer

The durable data layer is Prisma ORM pinned to **7.10.0** for both `prisma` and `@prisma/client` (npm's `latest` tag points at an 8.0.0-rc, so versions are pinned and verified against Next.js 16.3.4 / React 19.2.8). The `prisma-client` generator emits the client into `generated/prisma` — committed as app code, matching the Prisma 7 convention — and `prisma7.config.ts` holds the datasource and migration config. Runtime access is a single pooled Postgres connection wired through the `@prisma/adapter-pg` driver adapter, exported as a `PrismaClient` singleton from `lib/db/prisma.ts` (cached on `globalThis` in dev so hot reload doesn't open new pools). The schema in `prisma/schema.prisma` models every durable entity: Candidate, Problem (with difficulty, optional starter template, and sample/hidden tests as JSON), Session, Run, Message, Performance Summary (unique per Session), plus the durable auth rows PendingCode and AuthSession. The initial migration is committed under `prisma/migrations` and applied on deploy via `npm run db:migrate` (`prisma migrate deploy`); `npm run db:generate` (`prisma generate`) runs on `prebuild` and `postinstall`.

**Store selection.** With a configured `DATABASE_URL`, the app uses the Postgres stores (`PostgresDataStore`, `PostgresAuthStore`) and seeds the Problem set idempotently. Without one, production **fails fast** while development and the test suite keep the in-memory stores. The auth engine is constructed lazily (`getAuthEngine()`), so `next build` — which runs with `NODE_ENV=production` — still typechecks and collects page data without a database; the fail-fast throw happens at first request-time use, not at module load.

**One schema correction** was folded into the initial migration: `PendingCode` has no `candidateId`/Candidate FK, because a pending one-time code is issued before a Candidate exists — the code is keyed by mailbox email and upgrades into a Candidate only on verification. ADR-0002's async seams are what make these swap-in Postgres stores possible without touching callers.
