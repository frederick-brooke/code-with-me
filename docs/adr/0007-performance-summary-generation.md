# ADR-0007: The Performance Summary is a failure-soft, idempotent LLM call outside the managed agent

The Performance Summary is the Session's exit artifact: a written (never spoken) review covering what went well, even-better-if, problems, and a technical review of the final code, produced at Debrief from the whole Session Record. The spec and PRD (§5) ask for "the same LLM used in the Assessor", but the Assessor's LLM lives inside the ElevenLabs managed pipeline — there is no API to that exact model. We therefore make the summary a **dedicated OpenAI-compatible chat-completions call**, configured by the operator to point at the same provider/model the ElevenLabs agent is set to (`SUMMARY_LLM_BASE_URL` / `SUMMARY_LLM_API_KEY` / `SUMMARY_LLM_MODEL`). This keeps the same spirit — a capable conversational LLM fed the real trajectory — without coupling summary generation to the voice platform. The generator is a **client of the SessionEngine seam** (spec-mvp: the summary generator is a client like the UI and the tool endpoints); the engine itself stays UI-free and LLM-free, so it keeps testing headlessly with no keys.

## Decisions

- **Trigger is any move into Debrief, not a separate lifecycle event.** The summary is generated when a Session lands in the terminal phase — via the `end_session` tool (`POST /api/assessor/end/[sessionId]`) or `set_phase` to `debrief`. Both routes delegate to one orchestrator, `debriefSession` in `lib/summary/debrief.ts`, which owns generation + persistence. The `data` seam at `lib/data/` already had `PerformanceSummary` (unique per Session) with in-memory and Postgres implementations, so no schema change was needed.
- **Failure-soft, never blocks the end.** Ending the interview is an irreversible Candidate-facing fact; a summary that fails to generate must not undo it. `debriefSession` catches LLM errors, logs them, and leaves the Session ended with no summary. An unconfigured key skips generation silently (mirroring how the Assessor degrades). Re-running the end / a later `set_phase` to `debrief` retries because nothing is persisted.
- **Idempotent.** If a summary already exists for the Session it is returned untouched; the LLM is never called twice for the same Session.
- **The prompt is repo-versioned and leak-safe.** `SUMMARY_SYSTEM_PROMPT` (four required Markdown sections) and the user-message builder live in `lib/summary/prompt.ts`, assembled from `SessionEngine.getSessionRecord` — `{ session, problem, runs, messages, currentCode }`. Because the record structurally excludes hidden-test inputs and expected outputs (same rule as ADR-0001/0005), the summary call cannot observe hidden-test internals. The transcript is capped to its most recent 200 lines to bound token use.
- **Real history, not a template.** The record carries every Run (code + visible counts) and the transcript, so the summary reflects the Candidate's trajectory rather than the final code alone (spec-mvp: "the trajectory is what makes the summary non-generic").
- **Written artifact, never spoken.** The system prompt instructs that the output is written-only. The managed Assessor is not told to speak it, and the interview conversation is already over by the time the summary exists.

## Notes / future

`response_timeout_secs: 30` bounds webhook tool calls; awaiting generation within that is acceptable for the bounded prompt. A slower model, or a Candidate-facing "end" that should not wait, would move generation to fire-and-forget or a background job — a recorded upgrade path, not the MVP.
